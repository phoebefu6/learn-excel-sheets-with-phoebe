Lookups and the join you didn't know you made

Every analyst has typed VLOOKUP a thousand times, and most have typed it with three arguments. Leave out the fourth and both Excel and Google Sheets quietly switch to approximate match, which assumes the lookup column is sorted. Ferncastle's customer table is not. Tonight we take the lookup apart: what it compares, where it stops, what it returns when it finds nothing, and why every lookup you write is a join between two tables that you never had to name.

Part 1 · covers VLOOKUP's fourth argument

The argument you leave out decides the answer

5 min live

VLOOKUP takes four arguments: what to look for, the table to look in, which column to bring back, and how to match. The first three are the ones people remember. The fourth is the one that decides whether the answer is right, and it has a default.

LiveOmitted means approximate, in both apps3 min▶

Microsoft's VLOOKUP page is explicit: if range_lookup is not specified, "the default value will always be TRUE or approximate match". Google's page for Sheets says the same thing in its own words: "If is_sorted is not specified, it is TRUE by default", and TRUE there also means approximate. So =VLOOKUP(B2, customers!A$2:C$1371, 3) and =VLOOKUP(B2, customers!A$2:C$1371, 3, TRUE) are the same formula in both apps.

Approximate match is a real tool with a real job: banding a value into a tier table, like a discount that starts at R$ 100 and steps up at R$ 500. For that job, Microsoft's page says the first column must be "sorted alphabetically or numerically". Customer IDs are not tiers, and Ferncastle's customers.csv comes in export order, which is the order of each customer's first purchase: 2307, 9272, 789, 3082 and onward. Ask an approximate lookup to find a customer in that column and it will return a row. Often the wrong one, and nothing in the cell says so.

The habit is short: write the fourth argument every time. FALSE (or 0) for a key; TRUE only for a sorted tier table, and then on purpose. When exact match finds nothing, both apps return #N/A, which is the honest answer and the one you want to see.

Self-studyWhy "approximate" produces confident wrong rows3 min▶

An approximate search does not read the column top to bottom. It assumes the column is in order and jumps through it, deciding at each step whether the key lies above or below, and returns the last row that is not bigger than the key. On sorted data that is fast and correct. On unsorted data every jump can go the wrong way, and the search still lands on some row and returns its column 3.

Exactly which row it lands on is not documented by either vendor; they only promise correct results on sorted data. That is why the bench in session 6 calls its approximate search modelled: it uses a textbook binary search, so its wrong rows are a fair picture of the failure but not a prediction of the exact rows your app returns. What is not modelled is the conclusion: on an unsorted key column, approximate match is wrong by design, not by bad luck.

Real world

1,266 rows in the wrong state. On the bench, Dev's first build uses VLOOKUP with three arguments against Ferncastle's unsorted customer table. Of 1,565 order rows, 1,266 come back with a state that is not the customer's and 135 come back as #N/A, and SP revenue reads R$ 50,868.14 against a true R$ 80,469.61. The search is modelled, so your app's exact rows will differ; the scale of the damage from one missing argument is the point.

Part 2 · covers XLOOKUP and INDEX/MATCH

The same lookup, written three ways

5 min live

Every lookup does the same two things: search one column for the key, return the value from another column on the matching row. The three common ways to write it differ in what they default to, what they show when nothing matches, and which columns they can return.

LiveXLOOKUP: exact by default, and a name for "not found"3 min▶

XLOOKUP takes the search column and the return column separately: =XLOOKUP(B2, customers!A$2:A$1371, customers!C$2:C$1371, "NOT FOUND"). The argument order is the same in both apps. Microsoft's page says match mode 0, exact match, "is the default"; Google's page says match_mode is "0 by default". So the trap from Part 1 is gone: leave the match argument out and you get exact.

The fourth argument is the part to fall in love with. Microsoft calls it if_not_found, Google calls it missing_value, and in both it replaces the #N/A a failed match would show (Google states the default is "#N/A"). Put a word there, such as "NOT FOUND", and every row that matched nobody now says so in plain text that you can filter, count and show to Imogen.

One version note, stated exactly as Microsoft's page states it: XLOOKUP is not available in Excel 2016 and Excel 2019. If you are on one of those, use INDEX/MATCH below; it does the same job.

Self-studyINDEX/MATCH: write the 0, and look left when you need to4 min▶

INDEX/MATCH splits the lookup into its two halves. MATCH(B2, customers!A$2:A$1371, 0) searches column A and returns a position, such as 2 for the second row. INDEX(customers!C$2:C$1371, 2) returns whatever sits at that position in column C. Together: =INDEX(customers!C$2:C$1371, MATCH(B2, customers!A$2:A$1371, 0)), which works in both apps.

The 0 is not decoration. Microsoft's MATCH page says "The default value for this argument is 1", which finds the largest value less than or equal to the key and needs the column in ascending order: the same sorted-data assumption as approximate VLOOKUP. Type 0 finds "the first value that is exactly equal". The Sheets MATCH page is not among the pages read for these notes, so treat the default there as unchecked and write the 0 in both apps; it costs one character.

Because INDEX and MATCH each take their own column, the returned column can sit anywhere, including to the left of the one you search. VLOOKUP cannot do that: it always searches the first column of its table and returns from a column to its right. If you have ever rearranged a sheet's columns to make VLOOKUP work, INDEX/MATCH (or XLOOKUP) was the tool you wanted.

Real world

The same 94 rows, three ways. On Ferncastle's export, VLOOKUP with FALSE, XLOOKUP and INDEX/MATCH with 0 all agree: every row whose customer_id is a clean number finds its customer, and the same 94 rows find nobody. They differ only in what those 94 rows look like: #N/A from VLOOKUP and INDEX/MATCH, and whatever word you chose from XLOOKUP. Agreement between two methods is itself a check worth keeping in the sheet.

Part 3 · covers the lookup as a left join

Every lookup is a join

5 min live

When Dev fills a state column down orders.csv, he is doing what a database calls a left join: keep every row of the left table, and attach at most one value from the right table to each. Saying it that way predicts three behaviours the formula never announces: no row is added or removed, a repeated key returns only its first match, and a row that matches nothing still stays, carrying an error or whatever you replaced the error with.

LiveWhat "left join" predicts3 min▶

Fill a lookup down 1,565 order rows and you still have 1,565 rows. That is the first prediction: the left table never grows or shrinks, so a lookup cannot fix a grain problem. The 57 payment rows from session 1 are still there after the state arrives, each carrying its order's value and now its customer's state, ready to be counted twice.

The second prediction is about the right table. A left join attaches one value per row, so when the key repeats on the right side, something has to choose. Microsoft's XLOOKUP page says it returns "the first match it finds", and its MATCH page says type 0 finds "the first value that is exactly equal". Look up order 10002 in orders.csv to fetch its payment type and you get credit_card, from the first of its two rows; the voucher row is never reached. Neither vendor page read for these notes states the rule for VLOOKUP or for Sheets, so test it on order 10002 in your own app rather than assuming.

The third prediction is the dangerous one: a row that matches nothing still stays. It carries #N/A, which is loud, until someone makes it quiet.

Self-studyIFERROR is a silencer, not a fix4 min▶

Microsoft's page describes IFERROR exactly: it "returns a value you specify if a formula evaluates to an error; otherwise, it returns the result of the formula". It does not care which error, or why. =IFERROR(VLOOKUP(B2, customers!A$2:C$1371, 3, FALSE), "") turns every #N/A into an empty-looking cell, and Google's page notes that in Sheets, leaving out the second argument altogether returns a blank too (that one-argument form is Sheets only; Excel asks for both).

On Ferncastle, that blank lands on 94 order rows. A pivot of revenue by state then has nowhere to put them: they drop into a blank group or out of the total, and every state's figure is a little low. The sheet looks cleaner than before, which is precisely the problem. The professional norm is to make a failed match louder, not quieter: replace the error with a word, "NOT FOUND", and count it. If the count is not zero, the work is not finished.

Writing joins down by name, where a reviewer can read which rows were kept, is what SQL is for; session 5 covers when to hand the job over to the SQL course.

Real world

A spreadsheet in an economics argument. In 2013 Herndon, Ash and Pollin reported that Reinhart and Rogoff's widely cited 2010 analysis of public debt and growth had "coding errors, selective exclusion of available data, and unconventional weighting", and that corrected average growth for countries above 90 percent debt was 2.2 percent rather than about minus 0.1. How many countries a spreadsheet range left out, and Reinhart and Rogoff's reply disputing how much the correction changes their conclusion, are reported rather than read here. Both halves belong in the story: rows that quietly fell outside a calculation, and an honest disagreement about what the corrected number means.

Build-along

Bring the state across, four ways

★ 22 min · everyone builds

Open the orders.csv and customers.csv you downloaded in session 1, in Excel or in Google Sheets, and put customers on a second tab named customers. Orders keep their columns: A order_id, B customer_id, through I order_value, with the running count from session 1 in J. Customers has A customer_id, B city, C state, with 1,370 customers in rows 2 to 1371. Dev adds the state four ways and counts what each one does. The counts below are the bench's, computed from the same rows.

Set up and say what you expect. Check both tabs, then write the expectation down before any formula: every order row should find exactly one customer, so the state column should have 1,565 filled cells and no errors.

★ Step 1 · the setup, written downorders tab: A order_id, B customer_id, ... I order_value, J first_row_of_order customers tab: A customer_id, B city, C state (rows 2-1371, 1,370 customers) Expect: 1,565 order rows in, 1,565 out, one state each, 0 errors Note: customers is in export order, NOT sorted

Lookup one: VLOOKUP with three arguments. This is the formula most people write. Fill it down, then count its errors with a formula that works in both apps.

★ Step 2 · approximate, the default (column K, both apps)K1: state_approx K2: =VLOOKUP(B2, customers!$A$2:$C$1371, 3) fill down to K1566 Count #N/A: =SUMPRODUCT(--ISNA(K2:K1566)) Bench (modelled search): 135 #N/A. Your app's count may differ.

Lookup two: VLOOKUP with FALSE. Same formula, fourth argument written. Count the errors again. This count does not depend on how your app searches, so it should match exactly.

★ Step 3 · exact (column L, both apps)L1: state_exact L2: =VLOOKUP(B2, customers!$A$2:$C$1371, 3, FALSE) fill down to L1566 Count #N/A: =SUMPRODUCT(--ISNA(L2:L1566)) -> 94

Compare the two columns row by row. A helper column labels every row. Where both lookups found something and disagree, the approximate one is wrong, because exact match only returns the customer whose ID is equal to the key.

★ Step 4 · how many rows moved (column M, both apps)M1: approx_vs_exact M2: =IF(ISNA(L2), "exact missed", IF(ISNA(K2), "approx missed", IF(K2=L2, "same", "wrong"))) fill down to M1566 Count: =COUNTIFS(M2:M1566, "wrong") Bench, against cleaned keys: 1,266 wrong rows. Your count will differ: your app's search is its own, and this column skips the 94 rows exact missed. Any count above 0 means approximate match moved customers to the wrong state.

Lookup three: give the failure a name. XLOOKUP with a fourth argument puts a word where the error was. On Excel 2016 or 2019, where Microsoft's page says XLOOKUP is not available, use the INDEX/MATCH line instead: the label is what matters, not the function.

★ Step 5 · named not-found (column N)N1: state N2: =XLOOKUP(B2, customers!$A$2:$A$1371, customers!$C$2:$C$1371, "NOT FOUND") both apps (not in Excel 2016 or 2019) Or, in either app: N2: =IFERROR(INDEX(customers!$C$2:$C$1371, MATCH(B2, customers!$A$2:$A$1371, 0)), "NOT FOUND") fill down to N1566

Lookup four: count the named rows, then look at them. The count is your control number for the state column. Filter column N for NOT FOUND and read column B: you will see IDs such as "03082" on order 10004 and "7060 " with a space after it. Customer 3082 and customer 7060 are both in the customers table; their IDs in orders.csv are text. Session 3 repairs them.

★ Step 6 · the control number (both apps)=COUNTIFS(N2:N1566, "NOT FOUND") -> 94 = 67 zero-padded ("03082") + 27 trailing space ("7060 ") Wrong rows on the exact columns: 0 Rows still counted twice (session 1's 57 payments): unchanged

Keep the NOT FOUND count next to the column it checks. One cell that says 94 today and must say 0 before Monday. Delete K, L and M when you are done; keep N and its count. A lookup column without a not-found count is a join nobody has checked.

Homework

Before session 3

30 min
  1. Audit three lookups you rely on. In sheets you use at work, find three VLOOKUP formulas and check the fourth argument. For each one that is missing, write FALSE and note whether any result changed.
  2. Test the first-match rule in your own app. Look up order 10002 in Ferncastle's orders.csv with VLOOKUP FALSE, XLOOKUP and INDEX/MATCH 0, returning payment_type. Write down what each returns, and in which app.
  3. Hunt one IFERROR. Find an IFERROR that returns "" or 0 in a sheet you share. Replace the empty result with "NOT FOUND", count it, and write down the count, even if it is zero.

Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Dev writes =VLOOKUP(B2, customers!A$2:C$1371, 3) with no fourth argument. What does it do in Excel and in Google Sheets?

Microsoft's page says an unspecified range_lookup is "TRUE or approximate match"; Google's says is_sorted is "TRUE by default". Approximate match needs a sorted first column. On the bench, three arguments put 1,266 of 1,565 rows in the wrong state.

2 · Dev's exact lookup returns #N/A on 94 rows, so he wraps it in IFERROR(..., ""). The column now looks clean. What actually happened?

IFERROR returns the value you specify whenever there is an error, any error. A lookup is a left join: rows that match nothing stay. Making the failure louder ("NOT FOUND", then COUNTIFS = 94) is the professional norm; making it quieter is how rows go missing from a report.

3 · Looking up order 10002 in orders.csv to fetch payment_type returns credit_card, but the order was also paid by voucher. Why?

A lookup attaches one value per row, so a repeated key on the lookup side hands back only one of its rows: the first. The voucher row is never reached. Before looking up into a table, check that its key is unique with the running count from session 1.
