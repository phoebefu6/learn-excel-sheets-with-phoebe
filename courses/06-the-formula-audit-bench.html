Part 1 · covers the ladder and its counters

Five builds, one set of rows

5 min live

Each rung is a build an analyst could reasonably hand in. Rung 1 is VLOOKUP with the fourth argument left out, which both apps treat as approximate match. Rung 2 sets it to FALSE. Rung 3 cleans the order-side IDs with VALUE(TRIM()) and rebuilds the text dates. Rung 4 keeps only the first row of each order. Rung 5 cleans the table side too and refuses to report until revenue by state adds up to the distinct-order total.

LiveThree counters and one gap3 min▶

Rows silently wrong are rows that found a customer, just not theirs, so their revenue lands in the wrong state. Rows missing found nobody; the lookup returned #N/A and IFERROR turned it into a blank, which the pivot ignores. Double counts are the extra rows of an order paid in more than one part. A fourth counter, wrong late flags, counts orders whose late or on-time label is wrong because the delivery date was read as text or with day and month swapped.

The control gap needs none of that bookkeeping: revenue of the distinct orders minus revenue the pivot attributed to a state. It is positive when rows went missing, negative when rows were doubled, and only R$ 0.00 is a pass. On rung 3 the gap is minus R$ 6,021.59, the exact double count you found by hand in session 1.

Self-studyWhat the bench measures, and what it models3 min▶

Measured: every count and total, computed from the shipped rows by the engine in this page, and agreed with an independent Python implementation on all 217 numbers the bench can print (five rungs, with and without each trap). A comparison script proves it can fail by catching a planted 0.1 percent change.

Modelled, and printed on the widget: approximate match is a textbook binary search over the lookup column. Microsoft says approximate match needs the first column sorted, and Google names the argument is_sorted; neither promises anything on unsorted data, so a real app on this unsorted table returns wrong rows too, but not necessarily the same wrong rows. DATEVALUE is modelled under a month-first (US) date setting, which is the setting that makes day-first text fail; Microsoft and Google both say the result depends on that setting.

Real world

A spreadsheet in an economics argument. In 2013 Herndon, Ash and Pollin reported that Reinhart and Rogoff's widely cited 2010 analysis of public debt and growth had "coding errors, selective exclusion of available data, and unconventional weighting", and that corrected average growth for countries above 90 percent debt was 2.2 percent rather than about minus 0.1. Reinhart and Rogoff accepted the spreadsheet error and disputed how much it changed their conclusion (reported). Both things are part of the story: a range that left rows out, and a real disagreement about what the corrected numbers mean.

Part 2 · covers the anti-lever: approximate match

Why approximate match never helps here

5 min live

Approximate match does not scan the column. It assumes the column is sorted and halves it: look at the middle, decide which half the value must be in, repeat. On a sorted column that is fast and right. On Ferncastle's customers table, which is in the order customers first bought, it can look straight at the right row and still walk past it.

LiveThe default is the trap, in both apps3 min▶

Microsoft's VLOOKUP page: if you leave range_lookup out, "the default value will always be TRUE or approximate match", and approximate match needs the first column sorted. Google's: "If is_sorted is not specified, it is TRUE by default". MATCH has the same shape; its match_type defaults to 1, the largest value less than or equal to the one you asked for. XLOOKUP is the exception: its default match mode is exact, in Excel and in Sheets, which is the strongest argument for it on any version that has it.

So the anti-lever is not a weird setting someone has to choose. It is what you get by typing three arguments. On the bench it never improves a single number on any rung, which is the property that makes it an anti-lever and not a trade-off.

Self-studyThe honest nuance: when approximate is right3 min▶

Approximate match exists for a real job: banding. A sorted table of thresholds (0, 50, 100, 500) and a value of 73 should return the 50 band, and only an approximate search does that in one formula. The trap is using it on a key column, where "the nearest value not larger than this ID" means nothing at all.

So the rule is not "never approximate". It is: exact for keys, always written out (FALSE, 0, or XLOOKUP's default), and approximate only on a column you have sorted on purpose and whose meaning is a threshold. On Ferncastle there is no such column, which is why the anti-lever has no good side here.

Real world

A model that divided by a sum. JPMorgan's 2013 task force report on the London Whale losses described a value-at-risk model run through spreadsheets with manual copying and pasting, in which a formula, after subtracting an old rate from a new one, "divided by their sum instead of their average" (reported; the report itself was not reachable to read at source). Like approximate match, the formula returned a perfectly ordinary number every day.

Part 3 · covers the break button and the audited answer

One ID stored as text

5 min live

The break makes one small change, the kind a single paste makes: customer 8683, who lives in SP and has 10 orders in the file, is typed as text in the customers table. Rung 4 cleaned the order side of the join and not the table side, so it loses those 10 orders and keeps printing numbers. Rung 5 cleaned both sides and checks the totals, so it notices nothing because there is nothing left to notice.

LiveWhy the break is on the bench3 min▶

Without it, rungs 4 and 5 print identical numbers and the audit looks like ceremony. The break separates a build that happens to be right on today's file from a build that stays right when the file changes. Cleaning the side you suspect is a fix; cleaning both sides and reconciling is an audit.

Read what the break does to the earlier rungs too. Rung 2 goes from 94 missing rows to 103, rung 3 from 0 to 10. On rung 1 it changes nothing at all, because approximate match was already returning wrong rows for that customer. A build that is broken everywhere does not get any more broken, which is one more reason a single "looks fine" never tells you much.

Self-studyThe audited answer, written as a checklist3 min▶

Five lines, in order, on any lookup-and-pivot build. Grain and key of every table written down (session 1). Exact match written out on every lookup (session 2). Both key columns brought to one type, and dates rebuilt from their parts rather than guessed by DATEVALUE (session 3). One row per thing you count before you count it (sessions 1 and 4). And a reconciliation that must read zero before the number leaves your hands.

IFERROR stays allowed, but only after the reconciliation passes, and with a count of how many cells it is hiding printed next to the result. A blank that nobody counted is the most expensive cell in the sheet.

Real world

Gene names that became dates. The HGNC's 2020 guidelines for human gene nomenclature (Bruford and colleagues, Nature Genetics) record that "all symbols that auto-converted to dates in Microsoft Excel have been changed": SEPT1 is now SEPTIN1, MARCH1 is now MARCHF1. A scientific naming body renamed genes rather than wait for every spreadsheet to stop guessing types. A 2016 study had reported that about a fifth of papers with supplementary Excel gene lists contained such conversions (Ziemann and colleagues, reported).

Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · Moving from rung 1 to rung 2 (adding FALSE) takes wrong rows from 1,266 to 0 but missing rows from 135 down to only 94. Why are rows still missing?

Exact match either finds the right customer or nobody. The 67 zero-padded and 27 trailing-space IDs are text, the table holds numbers, so they find nobody until rung 3 applies VALUE(TRIM()). Every one of those customers is in the table.

2 · On clean data rungs 4 and 5 print the same answers. What does the break button show about the difference?

Identical answers on one file do not mean identical builds. The break changes the file the way a single paste does, and only the build that cleans both sides of the join and checks its totals keeps the right answer.

3 · A colleague says approximate match is fine because "it still found most of the right states". What does the bench say?

Approximate match reads the column as if it were sorted. On an unsorted key column it returns some customer's state for most rows, which is why the cells look plausible. It is the right tool for sorted threshold bands, not for keys.
