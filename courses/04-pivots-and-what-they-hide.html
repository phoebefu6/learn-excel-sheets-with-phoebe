Pivots and what they hide

A pivot table is the fastest honest-looking number in any spreadsheet. Drag a field into Rows, another into Values, and a tidy summary appears with a grand total at the bottom. What it does not show is what it counted. It groups rows, then summarises each group, and it never asks what one row is. Tonight we pivot Ferncastle's orders by state and find three different answers for SP alone, then build the one check that tells you which answer you are holding.

Part 1 · covers group by, then summarise

Group first, count second

5 min live

Every pivot does two things in a fixed order. First it sorts rows into buckets, one bucket per value of the Rows field. Then it runs one summary function inside each bucket: count, sum, average, distinct count. The bucket has no idea whether its rows are orders, payments or customers. It summarises exactly the rows it was handed, so the grain sentence from session 1 decides what every pivot cell means.

LiveCount, sum and distinct count are three different questions3 min▶

Look at the first nine rows of Ferncastle's orders.csv. Order 10004 and order 10005 both went to customer 3082 in MS, and both were paid in two parts, so MS gets four rows. Ask the MS bucket "how many?" and there are three honest answers: 4 rows, 2 orders, 1 customer. Ask it "how much?" and there are two: R$ 359.78 if you add order_value on every row, R$ 179.89 if you add it once per order. Only the second is revenue, because order_value repeats on every payment row of the same order.

A pivot will give you any of these. Count counts rows in the bucket. Sum adds a column over the rows in the bucket. Distinct count counts different values of a column in the bucket, which is the only one of the three that can count orders or customers on a table whose grain is payments. The tool does not choose for you in any meaningful sense; it picks a default, and a default is not a decision.

Self-studyWhat each app records about defaults and distinct count4 min▶

Excel. Microsoft's page on changing a PivotTable's summary function says Sum is "the default function for numeric values" and Count is "the default function for values other than numbers". Follow that through on Ferncastle: order_id is a number, so dragging it into Values gives you the sum of the order IDs, a large, confident and meaningless figure. The same page says Distinct Count "only works when you use the Data Model in Excel", so on an ordinary PivotTable built straight from the sheet it is not on the list. The exact wording of the option you tick to add the data to the Data Model is reported by secondary sources, not read here, so check the dialog in front of you rather than trusting a remembered label.

Google Sheets. A COUNTUNIQUE summary for pivot values is reported only: it appears in Google's Apps Script reference for pivot summary functions, not on the Docs Editors Help pivot pages read for these sessions. Sheets' default summary for a new value field is not recorded here either. The working rule in both apps is the same: read the summary label on every value field before you read its numbers, and never assume a distinct count exists until you have seen it work on rows you can count by hand.

Self-studyThe blank row at the bottom3 min▶

A pivot groups by whatever is in the Rows field, including nothing. If the lookup that adds state was wrapped in IFERROR(..., ""), every row that found no customer has an empty state, and the pivot puts all of them in one group with an empty label. On Dev's session 2 build, before the keys were cleaned, that group held 94 rows. It sits at the bottom of a list of 26 states, it looks like housekeeping, and a single filter click hides it for good. The label each app prints for that group is not recorded here; what matters is that it is a bucket of real orders with no state.

The professional habit is to make the bucket impossible to miss. Use a visible label such as "NOT FOUND" instead of a blank, as session 2 did, so the group has a name you can count with COUNTIFS. Then the pivot's job is to show a number for it, and yours is to make that number 0 before anyone sees the table.

Part 2 · covers counting rows is not counting orders

669 rows, 645 orders, 587 customers

5 min live

Scale the nine rows up to the whole file and the three answers stop being a curiosity. Grouped by state with a clean lookup, Ferncastle's 1,565 rows give SP 669 rows, 645 distinct orders and 587 distinct customers. All three are correct counts. Only one of them answers "how many orders came from SP?", and the pivot will happily print any of the other two under a heading that says orders.

LiveRead the three numbers for SP3 min▶

669 rows is what Count gives you on any field of orders.csv grouped by state. It counts payments. 645 distinct orders is the answer to Imogen's question: 24 of SP's rows are second or later payments of an order already counted. 587 distinct customers is a different question again: 58 of SP's orders came from a customer who had already ordered. RJ tells the same story at a smaller size, 226 rows, 221 orders, 200 customers, and MG 192, 183, 171.

Money follows the rows. Summing order_value over SP's rows gives R$ 83,204.30; summing it once per order gives R$ 80,469.61, which is the true SP revenue. The difference, R$ 2,734.69, is not an error in any formula. Every cell is right. The pivot simply added the same order's value once for every payment, which is exactly what Sum over rows means.

Self-studyOrders per customer inherits the same trap3 min▶

Imogen's second number is orders per customer. Divide rows by customers and you get 1,565 / 1,370 = 1.142. Divide distinct orders by customers and you get 1,508 / 1,370 = 1.101, the true figure. A ratio hides the double counting even better than a total does, because nobody has a feel for whether a repeat rate should be 1.10 or 1.14. Both look reasonable. Only one has a numerator at the right grain.

Remember too that Ferncastle's sample over-samples repeat customers on purpose (120 repeat customers alongside 1,250 one-order customers), so 1.101 describes this sample, not Olist as a whole. That is a second kind of "what does this number count?" and it belongs in the footnote of any figure you hand over.

Real world

Same research, different counts. Raymond Panko's summaries of spreadsheet-error studies are reported here, not read at source, and their headline figures vary by version: an older set of audits found errors in 24% of 367 spreadsheets, later field audits "at least 86%", a later summary 94% of 88. Part of the spread is what was counted. Some studies counted any error, some only serious ones; the samples were small and not random. Panko's caveat is the pivot lesson in another field: a count without a definition of what one unit is cannot be compared with another count.

Part 3 · covers totals that reconcile

A grand total is a claim; check it

5 min live

The grand total at the bottom of a pivot looks like proof. It is only the sum of the buckets above it, so it inherits every row the buckets double counted or dropped. The check is a second total computed a different way: revenue over distinct orders. Subtract the pivot's total from it and the sign of the result tells you which quiet path you are on.

LiveRead the sign of the gap3 min▶

Dev's pivot after session 3 groups all 1,565 rows by state and sums order_value. Its grand total is R$ 213,322.43. Revenue over distinct orders, the first row of each order only, is R$ 207,300.84. The control gap, distinct-order revenue minus what the pivot attributed, is minus R$ 6,021.59. Negative means the pivot attributed more money than the orders contain: rows counted twice. It is the same R$ 6,021.59 session 1 found by summing order_value with and without the running count, now showing up inside a pivot.

The sign is the diagnosis. On the session 2 build, before the keys were cleaned, the gap was plus R$ 4,671.89: rows went missing. That build was also double counting, so the positive number is net, the loss of 94 rows outweighing the 57 doubles. A gap of exactly R$ 0.00 is the only result that lets you hand the breakdown over, and it arrives when the pivot sums one row per order.

Self-studyWhere the check lives in the sheet3 min▶

Put the control total next to the pivot, not in your head. One cell holds distinct-order revenue, written with SUMIFS so a reviewer can read it: =SUMIFS(I2:I1566, J2:J1566, 1). A second cell points at the pivot's grand total. A third subtracts them and is labelled "control gap, must be 0.00". When someone refreshes the data next month and the grain changes again, that cell is the first thing that moves.

COUNTIFS and SUMIFS have the same argument order in both apps, read on both vendors' help pages: COUNTIFS(criteria_range1, criterion1, ...), and SUMIFS with the sum range first. That makes them the portable, checkable twin of any pivot cell. A pivot is quick to build and hard to audit; a COUNTIFS shows its criteria in the formula bar. Charts and dashboards built on top of a reconciled pivot are the job of the Business Intelligence sessions.

Real world

A total cannot show what is not in it. In October 2020 Public Health England said that "15,841 cases between 25 September and 2 October were not included" in reported figures, and stated the cause as "some files containing positive test results exceeded the maximum file size". PHE's statement does not name Excel or a row limit; press reports did. The lesson for a pivot is the shape of the failure: a daily total built from incomplete rows is still a clean-looking number. Only a second count, made independently, can show a positive gap.

Build-along

Pivot Ferncastle by state three ways

★ 22 min · everyone builds

Open the orders.csv and customers.csv you downloaded in session 1, in Excel or in Google Sheets, with the columns from session 3 in place: A order_id, B customer_id, through I order_value, the running count first_row_of_order in J, the cleaned key in L and the state from the exact, cleaned lookup in M. Dev pivots by state, then rebuilds every pivot cell with COUNTIFS and SUMIFS so it can be checked. Every number below is computed from Ferncastle's rows (constructed shop, derived Olist rows); your sheet should print the same.

Check the inputs before you pivot. A pivot is only as good as the column it groups by. Confirm that every row has a state and that the running count is still there.

★ Step 1 · inputsRows with a state label: =COUNTA(M2:M1566) -> 1565 Rows not found: =COUNTIFS(M2:M1566, "NOT FOUND") -> 0 First rows of an order: =COUNTIFS(J2:J1566, 1) -> 1508

Build the naive pivot. Insert a pivot table over A1:M1566. Put state in Rows, order_id in Values and order_value in Values. In Excel, order_id is a number, so its default summary is Sum: switch it to Count before reading anything. In Google Sheets, read the summary each value field shows and pick a count for order_id. Note the SP row and the grand total.

★ Step 2 · the pivot over every rowRows: state Values: order_id (Count) SP -> 669 Grand total -> 1565 order_value (Sum) SP -> 83204.30 Grand total -> 213322.43

Write the checkable twin. Next to the pivot, rebuild the SP cells with COUNTIFS and SUMIFS. They must match the pivot exactly. If they do not, one of the two is grouping something you did not expect.

★ Step 3 · the twin (both apps)SP rows: =COUNTIFS(M2:M1566, "SP") -> 669 SP sum over rows: =SUMIFS(I2:I1566, M2:M1566, "SP") -> 83204.3 Same as the pivot: yes, and both count PAYMENTS

Count orders with the running count as a filter. Drag first_row_of_order (column J) into the pivot's Filters and keep only 1. Every order now contributes exactly one row, so Count is a count of orders and Sum is revenue. Update the twin with a second criterion.

★ Step 4 · one row per orderPivot, filter J = 1: SP Count -> 645 SP Sum -> 80469.61 Grand total -> 1508 orders, 207300.84 Twin: =COUNTIFS(M2:M1566, "SP", J2:J1566, 1) -> 645 =SUMIFS(I2:I1566, M2:M1566, "SP", J2:J1566, 1) -> 80469.61 RJ -> 221 orders · MG -> 183 orders

Count customers the same way. A distinct count of customers needs a first-row marker for customers, built exactly like session 1's running count but on the cleaned key. This works in both apps on an ordinary sheet; Excel's Distinct Count needs the Data Model, and a COUNTUNIQUE pivot summary in Sheets is reported only.

★ Step 5 · first row of each customer (column Q)Q1: first_row_of_customer Q2: =COUNTIFS(L$2:L2, L2) fill down to Q1566 SP customers: =COUNTIFS(M2:M1566, "SP", Q2:Q1566, 1) -> 587 All customers: =COUNTIFS(Q2:Q1566, 1) -> 1370 RJ -> 200 · MG -> 171

Reconcile and write the check cell. Subtract what the pivot attributed from distinct-order revenue, first for the pivot over every row, then for the filtered one. Label the cell so the next person knows what it must say.

★ Step 6 · the control gapDistinct-order revenue: =SUMIFS(I2:I1566, J2:J1566, 1) -> 207300.84 Pivot over every row: =SUM(I2:I1566) -> 213322.43 Control gap: 207300.84 - 213322.43 -> -6021.59 (rows doubled) Pivot with J = 1: 207300.84 - 207300.84 -> 0.00 (reconciles) Orders per customer: 1508 / 1370 -> 1.101

Name the summary in the header. Rename the pivot's value headers to "orders (first rows only)" and "revenue R$, one row per order". A header that says what was counted turns the next reader's question from "is this right?" into "is this what I need?", which is a much faster conversation.

Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · In an Excel PivotTable, Dev drags order_id, which is a number, into Values and does nothing else. What does the field show?

Microsoft's page says Sum is the default for numeric values and Count for values other than numbers. order_id is numeric, so the pivot adds the IDs. Even switched to Count it counts rows, not orders, and Distinct Count needs the Data Model.

2 · Grouped by state, SP has 669 rows, 645 distinct orders and 587 distinct customers. Imogen asks how many orders came from SP. What is the answer?

The grain is one payment, so rows overcount orders. Customers undercount them, because 58 of SP's orders came from someone who had already ordered. The running-count filter (J = 1) or a COUNTIFS on it gives 645.

3 · Distinct-order revenue is R$ 207,300.84 and the pivot's grand total is R$ 213,322.43, so the control gap is minus R$ 6,021.59. What does the sign tell Dev?

The gap is defined one way round: distinct-order revenue minus what the pivot attributed. Negative means double counting, positive means rows dropped. Here the 57 extra payment rows add R$ 6,021.59, and filtering to first rows brings the gap to R$ 0.00.
