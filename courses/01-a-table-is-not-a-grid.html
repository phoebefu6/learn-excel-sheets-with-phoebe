Learn Excel & Sheets with Phoebe · Session 1 of 6

A table is not a grid

A spreadsheet will hold anything you type into it: a title in a merged cell, a subtotal halfway down, an ID that is a number on one row and text on the next. That freedom is why it never warns you. Tonight we draw the line between a grid, which a person reads, and a table, which a formula reads, and we find the one sentence every analysis should start with: what is one row? Then we open a real order export with 1,565 rows and discover it holds 1,508 orders.

Part 1 · covers grain and keys

One row, one thing: the grain

5 min live

A grid is laid out for a reader: a title on top, a header that spans two rows, a blank line to breathe, a subtotal where the month changes. A table is laid out for a formula: one header row, then one row per thing, every row the same kind of thing. The kind of thing is the grain, and until you can say it in a sentence, every COUNT and SUM you write is a guess about it.

LiveSay the grain in one sentence3 min▶

The grain sentence has one shape: "one row of this table is one ___." Ferncastle's export comes as three files. For customers.csv the sentence is easy: one row is one customer, 1,370 of them. For items.csv it is one item line of one order, 1,749 rows. For orders.csv almost everyone writes "one row is one order", and it is wrong. One row is one payment of an order. An order paid partly by card and partly by voucher appears twice, with its order value repeated on both rows. That is the real structure of the Olist data the export is derived from, not a mistake someone made.

The sentence matters because every aggregate inherits it. COUNTA over orders.csv counts payments. SUM of order_value adds the same order twice whenever it was paid twice. Nothing in the sheet changes colour when you do this; the number is simply a little too big, and it looks exactly like a right one.

Self-studyKeys: the columns that name a row3 min▶

A key is the column, or set of columns, whose value names exactly one row. In customers.csv the key is customer_id. In orders.csv, order_id is not a key, because it repeats; the key is order_id together with payment_seq. In items.csv it is order_id with item_no. Writing the key down is the grain sentence turned into something a formula can check: if the key repeats, the sentence was wrong.

The check is one formula you will use all evening: =COUNTIFS(A:A, A2) next to each row says how many rows share its key. Any value above 1 is a repeat. Session 2 shows the other half of this: a lookup assumes the column it searches is a key, and quietly returns the first match when it is not.

Real world

Payments are not orders. The public Olist dataset keeps payments in their own table, one row per payment instruction, because a single order can be split across a card, a voucher and more. Ferncastle's export joined that table to orders before sending it, which is how 1,508 orders became 1,565 rows. Exports built by joining a one-to-many table are the most common way a familiar file quietly changes its grain.

Part 2 · covers one type per column

One column, one type

5 min live

A cell holds two things: a value and a type. You see the value. The formula sees both. A column of customer IDs where most cells are numbers and a few are text looks uniform on screen and behaves like two different columns to every lookup that touches it.

LiveRead the type as well as the value3 min▶

Ferncastle's orders.csv stores customer_id as a number on most rows, and as text on 94 of them: 67 rows padded with zeros by the system that exported them ("00427") and 27 with a space typed or pasted after the digits ("427 "). Both look like 427. An exact lookup against the customers table, where the ID is the number 427, finds neither. Microsoft's own help pages walk through converting numbers stored as text with VALUE, and describe TRIM as removing all spaces except single spaces between words, which tells you how ordinary these cells are.

The working rule: one column, one type, checked rather than assumed. Before you trust a key column, count how many of its cells are numbers and how many are text; if both counts are above zero, the column is two columns sharing a header. Session 3 takes this apart properly, including the date column in the same file that is text from top to bottom.

Self-studyWhere mixed columns come from3 min▶

Three sources produce almost all of them. A system that pads IDs to a fixed width, so 427 leaves as "00427". A person who pastes a value copied from an email or a web page, bringing a trailing space with it (and sometimes the nonbreaking space, character 160, which Microsoft notes TRIM does not remove on its own). And an import that guesses each column's type from its first rows, so a column that starts with numbers is read as numbers until something breaks the pattern.

None of these raises an error. The mixed column only shows itself when something compares its cells with another column, which is exactly what a lookup, a COUNTIFS or a pivot does. That is why the type check belongs at the start of the work, next to the grain sentence, rather than at the end when a total looks odd.

Write the grain and the types at the top of your notes, not in your head. Two lines per file: "one row is one payment; key order_id + payment_seq" and "customer_id: number on 1,471 rows, text on 94". Anyone who reviews your sheet can now check the claim instead of trusting the layout.

Part 3 · covers silent failure and what the research says

Why the grid stays quiet

5 min live

A broken program stops. A broken spreadsheet keeps going and prints a number. There are three quiet paths from a real export to a plausible wrong answer, and every one of them ends in a cell that looks finished: a row matched to the wrong customer, a row that matched nobody and was hidden, and a row counted twice.

LiveWhat the research says, and how sure it is4 min▶

Raymond Panko has spent decades collecting studies of spreadsheet errors, and his summary is blunt: across many studies, errors are common and non-trivial. The headline figures are reported here, not read at source, and they vary by version of his paper: older field audits found errors in about a quarter of the spreadsheets examined, more recent audits in most of them (figures of 86 percent and above appear in later versions), and an average cell error rate of a few percent in the formula cells studied.

Teach the caveat with the number. The audits are small, the definitions of "error" differ (some counted only serious ones), and the spreadsheets audited were not a random sample of all spreadsheets. What holds across the versions is the mechanism, which is the part you can use: errors are made at a low steady rate per cell, and a large sheet has many cells, so the question is never whether a big sheet has an error, only whether anything would notice it.

Self-studyThe reconciliation habit3 min▶

Every aggregate you hand to someone should be checked against a total computed a different way. Revenue by state must add up to the revenue of the distinct orders. Orders per customer must use a count of orders and a count of customers that each match their own grain. When the two totals disagree, the size and sign of the gap tell you which path you fell into: positive means rows went missing, negative means rows were counted twice.

On Ferncastle's naive build the gap is R$ 11,364.04, made of all three paths at once. Session 6 lets you switch each path off in turn and watch the gap close to R$ 0.00. A reconciliation does not find the bug for you. It tells you, reliably, that there is one.

Real world

15,841 cases that were not in the total. In October 2020 Public Health England said that 15,841 positive COVID-19 cases between 25 September and 2 October had not been included in the reported daily figures, because "some files containing positive test results exceeded the maximum file size". PHE's statement does not name Excel or a row limit; press reports did. Either way, the reported figures were numbers, published daily, and nothing in them showed that rows were missing until someone reconciled them against the labs.

Build-along

Find the grain of Ferncastle's export

★ 22 min · everyone builds

Download the three files below, open orders.csv in Excel or import it into Google Sheets, and follow Dev through the six steps. The widget computes the same counts from the same rows, so you can check every number you get.

Open the file and say what you expect. Before any formula, write your guess at the grain in a cell above the data or in your notes. Most people guess "one row per order". Keep the guess; the point of the next steps is to test it.

★ Step 1 · the guess, written downFile: ferncastle-orders.csv Guess: one row = one order Key: order_id (if the guess is right, it never repeats) Check: count rows, then count distinct order_id

Count the rows. With order_id in column A and the header in row 1, count the non-empty cells below the header. The answer is the number of payments, not yet the number of orders.

★ Step 2 · rows=COUNTA(A2:A1566) -> 1565

Add a running count. In the first empty column, row 2, write a COUNTIFS whose range starts at the fixed top (the dollar sign) and ends at the current row. Fill it down. Each row now says how many times its order_id has appeared so far, so the first appearance is always 1.

★ Step 3 · running count (column J, both apps)J1: first_row_of_order J2: =COUNTIFS(A$2:A2, A2) fill down to J1566 Row 4 (the second row of order 10002) shows 2.

Count distinct orders. Count the rows whose running count is 1. If your guess were right, this would equal step 2. It does not.

★ Step 4 · distinct orders=COUNTIFS(J2:J1566, 1) -> 1508 1565 - 1508 = 57 rows repeat an order that already appeared

Look at one repeat and name the grain. Filter for order_id 10002. Two rows: payment 1 by credit card (R$ 61.19) and payment 2 by voucher (R$ 86.87), with order_value R$ 129.90 on both. The payments add up to more than the order value because they also cover freight. Now write the real grain sentence and the real key.

★ Step 5 · the grain, correctedGrain: one row = one PAYMENT of an order Key: order_id + payment_seq order_value repeats on every payment row of the same order payment_value does not

Prove what it costs. Sum order_value over every row, then over first rows only. The difference is the money a naive SUM counts twice. This pair of totals is your first reconciliation, and every later session reuses it.

★ Step 6 · the moneyEvery row: =SUM(I2:I1566) -> 213322.43 First rows only: =SUMIFS(I2:I1566, J2:J1566, 1) -> 207300.84 Double counted: 213322.43 - 207300.84 = 6021.59

Keep the running-count column. It costs one column and it turns every later formula into a choice you make on purpose: count payments, or count orders. Delete it and you will be making that choice by accident.

Homework

Before session 2

30 min
  1. Write the grain of three files you use. One sentence each, "one row is one ___", plus the key. Then test the key with the running count. Bring any file where the test disagreed with you.
  2. Type-check one key column. In Ferncastle's orders.csv, find a row whose customer_id is zero-padded and one with a trailing space. Then do the same on a key column of your own.
  3. Find a grid in the wild. A sheet in your organisation with a merged title, a blank row or a subtotal inside the data. Sketch how it would look as a table, with the totals moved underneath.
  4. Reconcile one number you reported. Recompute one total you have shared recently in a second, independent way. Write down the gap, even if it is R$ 0.00.
Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · Ferncastle's orders.csv has 1,565 rows and 1,508 distinct order_id values. What is its grain?

The repeats are not errors; an order paid by card and voucher really has two payments. Deleting them would lose payment information. The grain sentence names what a row is, and the key is whatever makes each row unique under that sentence.

2 · A customer_id cell shows 427, but an exact lookup against the customers table, where 427 is a number, returns #N/A. What is the likeliest cause?

A cell has a value and a type. Exact match compares both, so a number and the same digits stored as text are different values. In Ferncastle's export 94 rows are text: 67 zero-padded and 27 with a trailing space.

3 · Revenue by state on Dev's first build totals R$ 195,936.80; the distinct orders total R$ 207,300.84. What does the gap tell him?

R$ 11,364.04 is not rounding. A reconciliation does not name the bug, but a positive gap says money went missing, and on the naive build all three quiet paths contribute. The two totals must agree before the breakdown is trusted.
